# Accessibility scans

`/ext/a11y` runs axe-core over the app **only when asked**, groups the
violations by impact, and draws a box over one flagged element on request. Two
properties are invisible to jsdom and are the point of driving it: the box
stacks and passes clicks like the overlays' do, and the peer's absence is a
panel state rather than a crash.

## Sub-features

- `a11y-scan` runs axe on demand — from the panel button, `⌘K`, or the bridge —
  and never on a timer.
- `a11y-groups` lists the violations grouped by impact, worst first.
- `a11y-highlight` draws a box over one element, below the bar, taking no
  pointer events.
- `a11y-mask` keeps non-accessibility attribute values out of the panel, the
  clipboard and the bridge.
- `a11y-exclude` reports the app's violations and never the toolbar's own DOM.
- `a11y-unsupported` degrades to a documented panel state when `axe-core` is
  not installed.
- `a11y-load-on-scan` defers the peer's download to the first scan when the
  consumer passes `loadOn: "scan"`; the panel says "not checked yet" until then.

## How to get to it (user POV)

- Click the `a11y` chip to open its panel, then press **Scan this page**.
- Run `Scan this page for accessibility violations` from `⌘K`; `Export the last
  accessibility scan` and `Highlight a flagged element` declare an `input`, so
  the palette skips those two and leaves them to `/ext/agent`.
- Both work from inside the `⋮` menu when the bar is narrow.

## Driving it with the Browser pane

Preconditions:

- Baseline per [README](./README.md), viewport pinned to 1280×800.
- `axe-core` is a devDependency of `examples/playground`, so the peer is
  installed. `ext("a11y").status` is `"pending"` at baseline, `total` is `0`,
  `scans` is `0`, and `axeVersion` is a version string — the module is imported
  when the extension starts, which is not the same as having scanned.
- The playground's **Break accessibility on purpose** card ships exactly three
  violations: an alt-less `[data-testid="a11y-image"]`, an unlabelled
  `[data-testid="a11y-input"]`, and a low-contrast `[data-testid="a11y-faint"]`.
  They are not the only ones on the page: the **Drive the overlays** card ships
  an unnamed `[data-testid="overlay-unnamed"]`, an unlabelled
  `[data-testid="overlay-unnamed-input"]` and a positive-`tabindex`
  `[data-testid="overlay-tabindex"]` as fixtures for the focus-order overlay,
  and a scan counts those too. `extensions.tsx` turns axe's `region` rule off,
  because the demo cards are deliberately unlandmarked scaffolding.
- `color-contrast` is only evaluated for text axe considers **visible on
  screen**. The playground scrolls inside `.pg-scroll`, which sits in `.pg-app`
  — `height: 100vh; overflow: hidden` — and axe's visibility check treats an
  element whose box falls outside an `overflow: hidden` ancestor's box as
  hidden (`getOverflowHiddenAncestors` looks at `hidden` only, not `auto` or
  `scroll`; text scrolled out of a plain document is still checked). So from
  the top of the page at 1280×800 the a11y card (some 4 700 px down)
  contributes `image-alt` and `label` but **not** `color-contrast`. Scroll the card into
  view (`[data-testid="a11y-faint"]`, `scrollIntoView`) before a scan that is
  meant to see it. This holds with the Browser pane hidden as well: a hidden
  pane suspends `requestAnimationFrame`, not axe.

Throughout, `ext("a11y")` is
`read().diagnostics.find(d => d.id === "a11y").data` — the `A11yReport`, which
is the same object the panel renders:
`{status, running, at, durationMs, axeVersion, unsupportedReason, error, total,
counts, nodeTotal, passes, incomplete, groups, selected, scans}`.

- **Nothing runs until asked.** Read at baseline: `status: "pending"`,
  `scans: 0`. Wait ten seconds, read again: still `0`. A non-zero `scans`
  before any scan command is a finding.
- **Scan.** `runCommand("a11y.scan")` (or press the panel's
  `[data-dtb-part="a11y-scan"]`). Read: `status: "ok"`, `scans: 1`,
  `durationMs` a number, and — from the top of the page — `total: 4` over
  `nodeTotal: 5`: `button-name` (1), `image-alt` (1), `label` (2, both
  unlabelled inputs) and `tabindex` (1), the first three `critical` and the
  last `serious`. `counts` and `total` must agree — `total` is violated rules,
  `nodeTotal` is elements.
- **Scan with the fixture in view.** Scroll `[data-testid="a11y-faint"]` into
  view and scan again: `total: 5` over `nodeTotal: 6`, the fifth rule
  `color-contrast` (`serious`) with one node, `.pg-a11y-faint`. Driven
  2026-09-08 in both colour modes: `1.96:1` (`#b9b9b9` on `#ffffff`) in light
  and `2.47:1` (`#55585f` on `#16191e`) in dark, both against an expected
  `4.5:1`. A `color-contrast` node other than `.pg-a11y-faint` is a finding
  about the playground's own styles, not the extension — that is how the dark
  card links were caught at `3.74:1`.
- **It skips the toolbar.** No `groups[].violations[].nodes[].target` mentions
  `data-dev-toolbar`, and no rule reports the bar's own chips. The bar has
  contrast and naming of its own; if it appears here, the default `context`
  regressed.
- **The panel shows what the bridge returns.** Open the panel and read
  `[data-dtb-part="a11y-rule-id"]`: the same rule ids as `groups`, in the same
  order, worst impact first. Nothing in the panel may be absent from the report.
- **Highlight.** `runCommand("a11y.highlight", { rule: "label" })`, or press
  the rule's `[data-dtb-part="a11y-highlight"]` button. Read:
  `selected` is `"label#0"`. Page read: an
  `[data-dtb-part="a11y-box"]` exists inside
  `[data-dtb-part="overlay"][data-dtb-ext-id="a11y"]`, its rect matches the
  input's, and its computed `pointer-events` is `none`.
- **It stacks below the bar and passes clicks.** With the box drawn,
  `document.elementFromPoint` over the bar returns something inside the bar,
  never the box; then `left_click` `[data-testid="a11y-click-through"]` and
  watch its counter increment. Same assertions, same reasons as
  [overlays.md](./overlays.md) — this extension draws its own boxes rather than
  importing that one's.
- **Clear.** `runCommand("a11y.highlight")` with no input clears the box
  (`selected: null`); `runCommand("a11y.clear")` returns `status: "pending"`
  with `scans: 1` kept, so "never scanned" and "cleared" stay distinguishable.
- **Masking.** Grep the whole bridge read for the playground's own secrets (the
  three in [environment.md](./environment.md), plus the unlabelled input's
  `value`): none may appear. `[data-dtb-part="a11y-node-html"]` shows
  `value="[redacted]"` for the input, while `aria-*`, `class`, `id` and `type`
  survive verbatim — that is the policy, not a bug.
- **Deferred loading.** Open `/?a11y-load-on=scan` instead of `/` (the
  playground passes `loadOn: "scan"` for that page only; the default page keeps
  the eager import every other step measures against). Watch the network from
  before navigation: no request whose URL contains `axe-core` may happen
  before a scan, and the bridge reads `status: "pending"`, `scans: 0`,
  `axeVersion: null` — in eager mode `axeVersion` is already a string here,
  which is the one field that tells the two apart over the bridge. The panel
  shows `[data-dtb-part="a11y-unchecked"]` and an enabled Scan button, no
  `a11y-unsupported` and no error chip. Then `runCommand("a11y.scan")`: the
  chunk is requested, and the read is the same `status: "ok"`, `scans: 1`,
  `axeVersion` string and rule set as the eager scan above. `a11y.clear` after
  that returns `pending` **without** the unchecked note coming back — axe
  stayed loaded. This is `e2e/a11y.spec.ts`.
- **The missing peer.** `bun remove --cwd examples/playground axe-core`, restart
  the preview, and read: `status: "unsupported"`, `unsupportedReason` naming
  `axe-core` and the install command, `total: 0`, and the panel showing
  `[data-dtb-part="a11y-unsupported"]` with a disabled Scan button. No error
  chip for `a11y`, and `runCommand("a11y.scan")` still resolves. Reinstall
  afterwards — this is the one recipe step that mutates the app's dependencies,
  so it goes last and its cleanup is `bun install`.
- **Proof.** Capture the bridge read before and after the scan, the panel with
  its groups, the page read with the box's rect and `pointer-events`, the
  click-through counter either side of a click, and the secret grep.

## Gotchas

- A scan is **expensive**. `durationMs` on the playground is small, but a
  screenshot taken mid-scan can catch `running: true` and an empty `groups`;
  re-read rather than reporting a scan that found nothing.
- `total` counts violated **rules**, `nodeTotal` counts **elements**. A report
  with `total: 4` and `nodeTotal: 5` is not inconsistent — `label` alone has
  two nodes.
- A scan taken from the top of the page **does not include `color-contrast`**,
  and that is axe, not a regression: contrast is only computed for text that
  is inside the `overflow: hidden` `.pg-app` box at scan time (see the
  preconditions). A report that
  calls the fixture broken without first scrolling it into view is wrong; one
  that blames a hidden Browser pane is wrong too — the hidden pane reports the
  same five rules once the card is in view.
- `nodes` is capped (`nodeLimit`, default 5) and `truncated` says so; the count
  is always exact. Do not report the list's length as the number of problems.
- `status: "ok"` with `total: 0` means "the rules that ran found nothing", not
  "the page is accessible". The panel's empty state says as much; a report that
  upgrades it to a verdict is wrong.
- axe's impact for a rule can differ from the intuition — `label` is
  `critical`, not `serious`. Assert the grouping against what the report says,
  not against expectation.
- The box is drawn from the `overlay` slot, so it survives the chip collapsing
  into `⋮`; the panel button that set it does not. Set the highlight through
  the command if the chip is collapsed.
- An element axe reached through an iframe cannot be highlighted (its `target`
  is a path, and `querySelector` cannot follow one). It is listed and
  unhighlightable by design — not a broken button.
- The peer's absence has two shapes and both must degrade to `"unsupported"`:
  not installed at all, and installed-but-unresolvable by the consumer's
  bundler (Vite 8 emits a chunk that throws on import). Neither may produce an
  error chip.
